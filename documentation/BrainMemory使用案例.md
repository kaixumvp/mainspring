# BrainMemory 使用案例：一个「项目周期助手」的记忆怎么工作

> 配套可运行脚本：`example/brain_case_study.py`（零外部依赖，离线可跑）
> 全量基准对照：`benchmarks/memory_bench.py` + `benchmarks/bench_dashboard.html`

## 这个案例讲什么

一个助手 agent 服务多个项目。用户**过几周才回到同一个项目**（比如风控模型上线后隔三周再问结论）。
普通缓存（LRU）早把这条记忆踢掉了；BrainMemory 的机制是「**踢出热层但归档不删除**，
用户回来时自动想起来」。这个案例用三幕演示这三步，每一步都有肉眼可见的输出。

- 第 1 幕 · 活跃期：记忆被写入（写入选材 + 打分过滤闲聊）
- 第 2 幕 · 遗忘期：旧记忆被挤出热层 → 进冷层（归档，不删除）
- 第 3 幕 · 回归期：用户回来 → 冷层命中 → 提回热层 + 层级晋升

## 先跑起来

```bash
cd D:/project/mainspring

```

下面逐幕讲解（输出节选自本机真实运行，非编造）。

## 第 1 幕 · 活跃期：写入与过滤

脚本写了 4 条消息，巩固后只写入 3 条：

```
巩固写入 3 条（「下午好」这类闲聊被 importance 阈值过滤）
风控项目: 热层 2 条 / 冷层 0 条
    [热] tier=0.00 「风控模型 v2 上线后坏账率下降 0.8 个百分点，先别动参」
    [热] tier=0.00 「好的，风控模型结论已记录，报表偏好也会记住。」
```

**白话**：写入选材是 mainspring 自带 Consolidator 的活儿（BrainMemory 不管「写什么」，
只管「怎么写、怎么取、怎么丢」）。`importance_threshold=0.35` 把「下午好」这类
低分闲聊挡在门外——打分规则是关键词式的（偏好词 +0.3、够长 +0.1）。

> 学习要点 1：这个打分器的第一人称正则用了 `\b` 词边界，**纯中文文本里永远匹配不到**
> （汉字全被当作字母字符）。所以纯中文消息要过写入门槛，要么带偏好词
> （喜欢/希望/必须/总是……），要么够长（≥4 个空格分词）。案例第 2 幕的填充消息
> 特意带「必须/希望」就是这个原因——不带的话 16 条全被过滤，驱逐永远不会发生。

## 第 2 幕 · 遗忘期：挤出热层，归档不删除

16 个其它项目会话写入后（热层容量故意调到 8，让驱逐肉眼可见）：

```
16 个其它项目会话写入后：
风控项目: 热层 0 条 / 冷层 2 条
    [冷] tier=0.09 「风控模型 v2 上线后坏账率下降 0.8 个百分点，先别动参」
    [冷] tier=0.00 「好的，风控模型结论已记录，报表偏好也会记住。」
热层 8 格 / 冷层 8 格（容量 8）：旧项目条目被挤出热层 → 进冷层，归档不删除
命中统计: 热层命中=14 冷层命中=1 未中=0 驱逐=9 提回=1
```

**白话**：热层只有 8 个格子，新记忆进来就要按「价值」挤走最不值钱的。
风控项目的条目因为「很久没被用、预测近期也不会回来」价值最低，被挤进冷层。
**关键设计：被挤出去 ≠ 被删除**——人类遗忘是可访问性下降（想不起来），
不是信息丢失（还记得，只是难取）。冷层就是「难取的存档」。

**驱逐按什么排序**（一句话版）：`价值 = 还会不会再被用 × 现在抓不抓得住 × 丢了痛不痛`。
「还会不会再被用」由 topic 的回访规律预测，「抓不抓得住」随时间衰减
（越久没用越抓不住——这就是 L2 级联的稳定度阶梯），「丢不丢得痛」看冷层保真度。

## 第 3 幕 · 回归期：想起来

用户问「风控模型上线后的结论是什么」：

```
相似度 0.330 「风控模型 v2 上线后坏账率下降 0.8 个百分点，先别动参数」   ← 第一名，从冷层取回
相似度 0.158 「好的，风控模型结论已记录，报表偏好也会记住。」             ← 从冷层取回
冷层命中 4 次 → 提回热层（这就是『想起来』：被挤出去的记忆没有丢，取回时自动回到热层并晋升）
风控项目: 热层 2 条 / 冷层 0 条
    [热] tier=0.18 uses=3 「风控模型 v2 上线后坏账率下降 0.8 个百分点，先别动参」

再问一遍同一个问题（热层命中，不再付冷层取回代价）：
    [热] tier=0.27 uses=4 「风控模型 v2 上线后坏账率下降 0.8 个百分点，先别动参数」
```

**白话**：命中冷层 = 取回时多付一次「冷层代价」（重新读档/塞回上下文）；
提回热层后，同样的内容再被用就是热层命中（几乎零成本）。
每被用一次，tier 就升一点（0.09 → 0.18 → 0.27），对应人脑的「越用越稳」——
稳定度按对数阶梯增长（L2 离散级联），所以第 3 次用之后它比第 1 次更难被挤走。

> 学习要点 2：相似度数字（0.330）来自脚本内置的**占位 embedding**（哈希 n-gram），
> 绝对值没有意义，只有**排序**有意义。真实部署要注入你们自己的 embedding 模型
> （实现 `mainspring.ports.Embedder`，构造时 `BrainMemory(embedder=你的实现)`）。
> 这正是端口设计的目的：记忆机制与向量化能力解耦。

## 收尾 · 自证与性能

```
tier 分位 [0.0, 0.0, 0.18]（跨度 0.27，恒 0 就是套壳 FIFO）
M' 分位 [0.05, 0.573, 0.824]（铺开 = 存储强度有差异，没饱和）
性能: query p99=0.052ms，QPS≈4.2 万（进程内）
```

**白话**：这两行是防骗自检。如果这套实现其实是个「先进先出」的假货，
tier 会恒等于 0、M' 会全部饱和到同一个值——看到跨度非零，才说明记忆状态是真的。

## 三个大白话数字与全量对照

案例讲机制，全量对照看数据：

```bash
.venv/Scripts/python benchmarks/memory_bench.py   # 3 regime × 3 seed + 消融，约 4 分钟
```

然后浏览器打开 `benchmarks/bench_dashboard.html`。三个必看数字：

| 数字 | 含义 | 本次实测 |
|---|---|---|
| 热层命中率 | 查询直接命中热层的比例 | phased：0.633 vs LRU 0.501 |
| 总召回率 | 热层+冷层合计找到的比例 | 与 LRU 持平（不丢信息） |
| 相对 LRU 效用 | 综合收益（含冷层代价与整理成本） | phased +11.6% / 平稳 +2.4% / 轮换 −4.7% |

**诚实预期**：平稳场景 ≈ LRU（+2.4%，白买）；组级轮换更差（−4.7%，证伪栏）；
只有「过段时间回到同一主题」的场景才显著赢（+11.6%）。
如果你的助手是平稳问答，LRU 就够——这是设计结论，不是缺陷。

## 参数白话表

| 参数 | 管什么 | 什么时候动它 |
|---|---|---|
| `hot_budget` | 热层格子数（内存/槽位成本） | 越大热命中越高、越贵；按预算定 |
| `archive_value` | 冷层命中折算的价值 | **止损线**：≈0.35 以下模型才值得买；冷层免费（=1）时 LRU 就是最优 |
| `lookahead` / `topic_halflife` | 时间尺度（事件数单位） | **接真实日志时必须重标定**——合成基准的单位和真实事件率不同 |
| `fidelity` | 冷层取回时的有损折扣 | 默认 0.7，实测调它收益 ≤0.5pp，别优化 |
| `item_weight` / `min_cluster` | 被实测否决的机制开关 | **保持默认 0 / 1**（关），它们只在消融里当负对照 |
