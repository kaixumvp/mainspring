# Mainspring · 版本规划（Roadmap）

> 本文档统一归档于仓库根的 `documentation/mainspring/`。

> 本文档从平台《SmartAgent 平台 · 版本规划》中**拆出框架层部分**。原平台规划描述的是「业务层 + 框架层」合并的单体演进；Mainspring 已独立成包（`pip install mainspring`），因此按自身语义化版本演进。
>
> **范围**：仅 `mainspring` 包自身的能力。业务层的 HTTP 入口、多租户、鉴权数据、持久化、RAG 流水线实现、Console、K8s 部署**不在本文档范围**，见 [PlatformAgent 业务层详细设计](../platformagent/业务层详细设计.md)。
>
> 当前版本：**v3.6.0**（对应平台 0.3.0；v3.0 完成全量改名 `ouroboros` → `mainspring`，v3.1 交付结构化输出，v3.2 交付 `@tool` 装饰器，v3.3 交付 Checkpointer 官方实现，v3.4 交付 v2.3「开发者体验」的文档站与 DevUI，v3.5 交付请求级上下文预算治理，v3.6 交付重构 P1：上下文治理收敛 + 依赖瘦身，见 §二）

## 〇、拆分边界：什么归框架，什么归宿主

平台规划里的每个模块都被这条线切成两半——**机制（Mechanism）归框架，策略与 IO（Policy & IO）归宿主**。

| 平台模块 | Mainspring（框架）负责 | 宿主（业务层）负责 |
|----------|----------------------|-------------------|
| LLM Gateway | `LLMGateway` 协议 + LiteLLM 默认实现 + 路由/fallback 装饰器 | 密钥管理、厂商配额、成本核算 |
| Agent Runtime | 运行循环、状态机、迭代/深度/超时控制 | Run 记录落库、异步任务调度 |
| 插件体系 | `Plugin` 协议、`PluginManifest`、`PluginRegistry`、ref 解析 | 从 DB 装配插件（`db_plugin_loader`） |
| Skill Manager | 四形态 Skill 的**执行** | Skill 的注册 / 版本 / 绑定 CRUD |
| Tool Manager | Builtin / MCP / HTTP(OpenAPI) 工具的**执行** | 工具的租户级配置与凭据 |
| Brain / 记忆 | Working Brain、Consolidator、`LongTermMemory` 端口、召回编排 | pgvector 实现、DB 会话 |
| Knowledge | `Knowledge` / `Retriever` 端口 + `kind="knowledge"` 插件形态 | RAG 摄取/切块/embedding/Rerank 流水线、KG 存储 |
| Workflow / 可靠性 | Retry、熔断、超时、Pause/Resume 机制、`Checkpointer` 端口 | checkpoint 持久化、HITL 审批单据与通知 |
| 权限（IAM） | `check_permission()` 纯逻辑 + `PermissionChecker` 端口 | RBAC/Grant 数据加载、`PermissionContext` 构建 |
| 事件 | `RuntimeEvent` 数据模型 + `EventSink` 端口 | SSE/WebSocket 传输、事件落库 |
| Observability | span/metric 埋点（仅依赖 `opentelemetry-api`） | Collector、Prometheus、Grafana、Langfuse |
| Evaluation | 确定性重放、`Judge` 端口 | Golden Set 管理、A/B、报表 |
| Console / 部署 | — | 全部 |

> 判据：**框架能否在没有数据库、没有 HTTP、没有租户概念的情况下单测通过**。能，就归框架。

## 二、各版本详细说明

### v0.1 骨架版 ✅

**目标**：证明 `Plan → Decide → Execute → Observe` 循环可行。

| 模块 | 交付内容 |
|------|----------|
| `llm/` | `LLMGateway` 协议 + `LiteLLMGateway`（单厂商）+ `LLMResponse`/`ToolCall`/`Usage` |
| `core/` | `Plan → Decide → Execute → Observe` 四节点 + `AgentState` |
| `tools/` | `BaseTool`/`ToolResult` + `calculator`(AST 白名单) / `http` |

**验收**：多轮对话 + ≥1 次工具调用成功；有迭代上限，不死循环。

---

### v0.2 能力版 ✅（当前 0.2.0）

**目标**：从「写死一个 Agent」到「宿主组装 Agent」，并从平台单体中**独立成可发布的包**。

| 模块 | 交付内容 |
|------|----------|
| `plugins/` | `Plugin` 协议 + `PluginManifest` + `InvokeContext` + `ToolAsPlugin` 适配 + `PluginRegistry`（裸名 / `kind:name@version` / `function_name` 三键索引）+ ref 解析 |
| `skills/` | 四形态 `prompt` / `function` / `flow` / `agent` + `SkillManager.build()` + `skill_` 前缀命名空间隔离 |
| `tools/` | MCP 客户端（JSON-RPC 2.0 over streamable HTTP）+ HTTP(OpenAPI) 工具生成 |
| `memory/` | `WorkingBrain`（Redis 滑窗 + TTL）+ `Consolidator`（规则抽取 + 0.85 相似度去重）+ `MemoryManager` 门面 |
| `ports.py` | `check_permission()` 纯逻辑 + `PermissionChecker` / `WorkingMemory` / `LongTermMemory` / `MemoryEntry` |
| `core/nodes/execute.py` | **执行前**强制授权（不信任 LLM 的选择） |
| `events/` | 运行时事件（`run.started` / `step.completed` / `run.completed` / `run.failed` / `run.awaiting_human` / `run.approved` / `run.rejected`） |
| `log.py` | `mainspring` 命名空间 + `NullHandler`，框架不自行配置 handler |
| 工程 | 从 `smartagent` 单体拆出，src layout，独立 `pyproject.toml`，55 个单测全部 fake 依赖（无 Redis/LLM/DB） |

**验收**：宿主不改框架核心，仅「注册 Skill/Tool + 配置 Agent」即可上线新场景；越权调用被 `execute` 拦截；高危插件返回待审批。

---

### v0.3 收口与可靠版 ✅

**目标**：把 v0.2 遗留的架构债还掉（端口收口、门面收口、传输解耦），并让长任务真正**可重试、可暂停、可介入**。

| 方向 | 交付内容 |
|------|----------|
| **端口收口** | 把散落的 `LLMGateway`(`llm/base.py`)、`Embedder`(`llm/embedder.py`)、`Plugin`(`plugins/base.py`) 全部收进 `ports.py`；补 `EventSink` / `SubagentRunner` / `FlowRunner` / `Checkpointer` 端口。目标：`import mainspring.ports` 一处看全框架↔宿主契约 |
| **`AgentRuntime` 门面** | `AgentRuntime.run(definition, task, context, deps) -> RunResult`；引入 `AgentDefinition` / `RunContext` / `RuntimeConfig` / `RuntimeDeps` / `Step` / `RunResult` 强类型，取代当前的裸 `dict` 出入参 |
| **事件解耦** | `events/sse.py` → `events/events.py`：框架只产出 `RuntimeEvent` 对象，**SSE 序列化下沉宿主**；`EventSink` 端口取代 `on_step(dict)` 回调 |
| **可靠执行** | 节点级 Retry（指数退避）+ 熔断；`RuntimeConfig.timeout_seconds` 真正生效；`max_subagent_depth` 真正强制（当前仅有注释与状态字段，无强制） |
| **暂停 / 恢复 / HITL** | 接入 LangGraph checkpointer（经 `Checkpointer` 端口，持久化留宿主）；高危审批从「返回 `[approval required]` 字符串后继续跑」升级为真正 `pause → awaiting_human → resume(approvals)` 同 run 续跑 |
| **记忆增强** | Memory Graph 结构、`reflect` 重要度评分、遗忘策略、`sufficiency` 充分性判定；知识不足时回退 Knowledge 端口并回写沉淀 |
| **知识端口** | `Knowledge` / `Retriever` 端口 + `kind="knowledge"` 插件形态（RAG 流水线实现由宿主提供） |

**兼容性**：`build_graph` / `run_agent` 保留一层 deprecated shim，v1.0 移除。

**验收**：
- 任一 run 可从 checkpoint 恢复，且恢复幂等
- 高危插件触发 `awaiting_human`，`resume` 后在**同一 run** 内继续
- 工具瞬时失败自动重试；run 超时可中止；子 Agent 递归超深被拒
- 框架↔宿主的全部契约集中在 `ports.py`

**依赖**：v0.2

### v0.4 可观测与安全版 ✅

**目标**：框架侧具备生产可观测性，补齐 v0.2 明确标注为「非安全边界」的执行面。

| 方向 | 交付内容 |
|------|----------|
| **链路追踪** | 每节点 / 每插件调用产出 OTel span，`trace_id` 经 `InvokeContext` 全程透传；框架只依赖 `opentelemetry-api`，且为**可选依赖**（未安装时降级为 no-op） |
| **指标** | 迭代数、工具时延、token 用量、失败率经 `Metrics` 端口暴露，宿主接 Prometheus |
| **执行沙箱** | `FunctionSkill` 当前用 `exec` + 受限 builtins，代码内已注明「不是安全边界」——本版落地子进程/容器沙箱，或改为显式 opt-in 的可信模式 |
| **注入防护** | Prompt 注入基础防护（工具结果与用户输入的边界标注）；敏感信息脱敏范围从日志扩展到事件与 span |
| **韧性** | 多厂商路由 + fallback（以 `LLMGateway` 装饰器实现，不污染核心）；`tool_call` 解析容错与结构化输出兜底 |
| **并发** | 单轮 LLM 返回多个 `tool_calls` 时并行执行 |

**验收**：一次 run 的全链路 span 完整可回溯；FunctionSkill 逃逸测试通过；主厂商故障自动 fallback 且被 span 记录。

**依赖**：v0.3

**验收**：宿主升级 minor 版本无需改代码；破坏性变更只出现在 major。

**依赖**：v0.4

### v2.0 包名归一 ✅

**破坏性变更**：导入包名 `src` → `ouroboros`。

发行包 `ouroboros` 此前导出的顶层包字面就叫 `src`。这不是风格问题：宿主如果是 src-layout
（本仓库的业务层就是），把宿主根放进 `sys.path` 后 `import src` 会**静默**绑定成宿主自己的
命名空间包，同一个文件被双地址化（两套 `@lru_cache` 单例、两套 `DeclarativeBase` 注册表）。
`src` 也是它不拥有的顶层名字，PyPI 上已被占用。

| 方向 | 交付内容 |
|------|----------|
| **包名归一** | `src/` → `ouroboros/`；`from src.x` → `from ouroboros.x`；日志命名空间 `src` → `ouroboros` |
| **契约兑现** | 使实际包名与 v1.0 冻结时声明的「顶层 `ouroboros`」终于一致（此前从未一致过） |
| **依赖瘦身** | 移除无人 import 的 `langgraph` 及其 7 个传递依赖 |

**兼容性**：`__all__` 里的公共符号一个未动，仅包名前缀变化。详见 `CHANGELOG.md` 的 2.0.0 段
（附逐条替换对照表）。

**验收**：`import ouroboros` 可用；宿主 `conftest.py` 不再需要任何框架相关的 `sys.path` 注入；
168 个单测全绿。

**依赖**：v1.1

### v2.1 流式与上下文治理版 ✅

> 原 v2.1 编号原计划给多智能体；多智能体降级为 v2.4（见版本总览表下方说明），本编号用于 2026-11 竞品分析后的最高优先级缺口。

**目标**：补齐「没有流式就没法用」与「长任务必爆窗口」两个硬缺口，并把 Plan 的固定开销变成 opt-in。

| 方向 | 交付内容 |
|------|----------|
| **流式输出** | `StreamingLLMGateway` 可选协议（`ports.py`）+ `ChatChunk` / `ToolCallDelta`；`LiteLLMGateway.chat_stream` 归一化分块（含 tool-call 分片按 index 聚合、`stream_options.include_usage` 失败自动重试）；Decide 边流式边发 `message.delta` 事件；`llm/stream.py` 折叠为与 `chat()` 相同的 `LLMResponse`，下游步骤与流式无关 |
| **装饰器透传** | `FallbackLLMGateway`（首块前才 failover；流中错误直接抛，避免换厂商重复输出）、`FaultTolerantGateway`（首块前降级 `on_error` 单块）、`RecordingGateway`（转发中记录折叠响应）、`ReplayGateway`（录制响应合成单块流） |
| **上下文治理** | `ContextManager` 端口 + `mainspring/context.py` 的 `SlidingWindowContext`（头部 system 保留、切点跳过孤立 tool 消息、超长工具结果截断）；`RuntimeDeps.context_manager` 注入自定义策略，`RuntimeConfig.max_history_messages` 零配置启用；被压缩历史**永久丢弃** |
| **Plan opt-in** | `RuntimeConfig.enable_planning=False` 默认关闭（省一次 LLM 调用/ run）；记忆召回上下文改由 Decide 注入，plan 开关不影响召回链路；需要旧行为显式开启 |

**验收**：流式与是非流式产出同一 `LLMResponse`；未注入 sink 时零开销回退 `chat()`；滑窗切点不产生孤儿 tool 消息；168+ 全量单测全绿（含新增 `test_streaming.py` / `test_context_window.py`）。

**兼容性**：新增 API 均为可选协议与带默认值配置，宿主零改动即可升级；唯一行为变更是 Plan 默认不再执行（CHANGELOG 明示，显式 `enable_planning=True` 恢复）。

### v3.0 改名 mainspring ✅

**破坏性变更**：发行名与导入包名同步 `ouroboros` → `mainspring`（PyPI 上 `ouroboros` 已被生信包占用、`ouroboros-ai` 被占且定位撞车；外部用户为零，dist + import 一次到位，不再分两步）。

| 方向 | 交付内容 |
|------|----------|
| **包名归一** | `ouroboros/` → `mainspring/`；`from ouroboros.x` → `from mainspring.x`；日志命名空间 `ouroboros` → `mainspring` |
| **打包元数据** | `pyproject.toml` name/version/description/packages 更新；Poetry 依赖改为 `mainspring = { path = ... }`；CHANGELOG 新增 3.0.0 段（附逐条替换对照表） |
| **宿主迁移** | 平台业务层 backend 源码 / tests / pyproject / poetry.lock / Dockerfile 引用全部迁移，`conftest.py` 无框架相关 `sys.path` 注入 |

### v3.3 Checkpointer 官方实现 ✅（当前）

原 v2.2「持久化补齐」全部交付：`Checkpointer` 端口（save/load/delete + list_runs）的三个官方持久化后端，与 `InMemoryCheckpointer` 行为完全互换。

| 方向 | 交付内容 |
|------|----------|
| **SQLiteCheckpointer** | stdlib `sqlite3`，零依赖零配置；单文件单表，WAL + `busy_timeout=5000`，每次操作独立连接（低频路径，比连接池简单安全），跨进程安全；`:memory:` 显式拒绝 |
| **RedisCheckpointer** | 注入 `redis.asyncio.Redis`（与 `WorkingBrain` 同模式，框架不建连接）；键前缀 `cp:` 可配；TTL 默认关闭（过期即丢快照与 resume 语义冲突），显式 `ttl_seconds` 才开启 |
| **PostgresCheckpointer** | 接受宿主提供的任意 DBAPI 2.0 连接（psycopg2/psycopg/…），`import mainspring` 永远不依赖 PG 驱动；表懒建（`CREATE TABLE IF NOT EXISTS`，可与宿主迁移表共存） |
| **共享 JSON 信封** | `checkpoint/codec.py`：`{"schema_version": 1, "state": ...}`；版本不符/载荷损坏在 `load` 时抛 `ValueError`（响亮失败，绝不静默用错状态 resume） |
| **快照语义对齐** | `load` 返回深拷贝（宿主改返回值不影响已存快照）、save 覆盖、`list_runs` 排序稳定——换后端不改 resume 语义 |

**验收**：`tests/test_checkpointer.py` 34 项——7 个共享语义用例 × 4 后端（memory/sqlite/redis/postgres，Redis 与 PG 用 fake，套件零外部依赖）+ 信封用例 × 3 持久后端 + SQLite 重开耐久/`:memory:` 拒绝 + Redis 键名/TTL；框架与业务层全量单测全绿。

**兼容性**：纯新增 API，宿主零改动。

**边界**：官方后端各自维护 `checkpoints` 表/键，**不替代**「快照与状态翻转同事务」的需求——需要 status+snapshot 原子性的宿主应自行实现端口（业务层 `DbCheckpointer` 即此模式），官方后端用于零配置/单服务场景。

**依赖**：v3.2

## 六、演进原则

1. **框架不反向依赖宿主**：不 import 宿主的 HTTP / DB / 配置 / 租户概念；新增能力先问「这条能不能在纯内存单测里跑通」。
2. **端口先行**：需要外部 IO 的能力，一律先在 `ports.py` 定义 Protocol，再考虑要不要给默认实现。
3. **默认可跑**：每个端口尽量配一个零配置的默认/降级实现（如 `HashEmbedder` 之于 `LiteLLMEmbedder`），保证 `pip install` 后能直接跑通示例。
4. **容错收敛**：LLM 失败退化为单步计划、空输出即收尾、迭代上限兜底——新增节点必须给出兜底路径。
5. **测试无外部依赖**：Redis / LLM / DB 一律 fake，`poetry run pytest` 在无网环境必须绿。
6. **SemVer 与弃用**：v1.0 起破坏性变更只进 major；弃用至少跨一个 minor 并在 CHANGELOG 标注。
